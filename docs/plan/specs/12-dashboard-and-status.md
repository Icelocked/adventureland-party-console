## How to read this spec

The dashboard is the browser page the player uses to watch and steer the party. It has no
decisions of its own to make: every number and sentence on it comes from a character's status
report, a coordinator owner's state, or a fixed copy of a game or runtime rule, and every button
posts to a coordinator route. This spec maps three things:

1. **How data reaches the page** (1.1 to 1.5): what each character reports, how the coordinator
   stores it, the eight polled sections and their intervals, the 304 revisions, the live stream, the
   map stream, logs and metrics, and the action client that posts every button.
2. **Where every status text comes from** (the short version below, and each behaviour's rules):
   the Hunt's stage and free-text message, merchant job labels, convoy text, logs, and the fork's
   activity label that rebuilds other owners' state.
3. **Every screen element** (1.6 to 1.18), one behaviour per panel, dialog, control or shared
   helper, with the routes it posts and the fields it reads.

## 1. What it does today

### The short version

- **Every status report is also the coordinator's tick.** A character posts its status to
  `POST /party-api/status` every heartbeat. The handler stores it and then runs grouped combat, rare
  hunting, bankboi, anniversary, the Hunt tick, the farm area tick, scatter, events, market
  publication, the convoy step and merchant scheduling before it replies (ingestion.ts:110-137,
  DSH-001). Dashboard data and party decisions arrive through the same request.
- **The page reads eight sections by polling** `GET /party-api/state?section=...&dashboard=1`:
  core every 1 s, config every 15 s, fast every 250 ms and inventory every 2 s (both only while the
  live stream is down), logs 1 s, bank 2 s, market 10 s, mail 2 s, catalog once per reference
  revision (query-cache.tsx:172-186, DSH-021). Bank, logs and market answer 304 while unchanged
  (section-revision.ts:18-26, DSH-008). Polling stops while the tab is hidden.
- **Vitals, position and inventory come from a live stream** (`/party-api/dashboard-stream`,
  DSH-015, DSH-019). A character sends fast telemetry every 100 ms only while some dashboard holds a
  stream lease (DSH-005, DSH-035). Maps have their own per-character stream fed by map frames
  (DSH-016, DSH-040).
- **Every button posts through one action client** (`performAction`, query-actions.ts:111-155,
  DSH-024) that cancels and refreshes exactly the sections a route changes. Seven coordinator writes in
  seven files bypass it with plain `fetch` (2.4).
- **Status text has no owner.** The coordinator has no status text API. Each owner writes its own
  free-text field, and each reader picks what to show:

## 2. What goes wrong

### 2.0 Root causes

The data path itself is in good shape. The query cache, the action client, the live stream and the
304 revisions carry few fix commits (`git log --oneline refs/review/ryan-1.5 -- <file> | grep -ci fix`:
query-cache.tsx 0 of 5, dashboard-live.tsx 0 of 4, dashboard-stream.ts 2 of 8, query-actions.ts 3 of
11, public-state.ts 3 of 15), and each has its own unit tests (section 4). The problems sit around it:

1. **No status text owner.** Owners write free text next to a state enum and nothing sets which of
   two reasons wins (2.1, bug 13). Readers choose for themselves: Ryan's Hunt line prints both the
   stage and the message (farming-mode-control.tsx:256-260), the merchant job label keeps its own
   copy of the routine names (DSH-164), and the fork's strip label parses message prefixes
   (HEAD character-activity.ts:82-85). Convoy progress has no reader on Ryan's dashboard at all.
2. **Sections are split by how often a field changes, not by what it is.** The config section
   (15 s) carries `farmingProfiles`, which holds every profile's live controller state: the Hunt
   cycle, the convoy, the farm area, combat recovery and grouped combat (hunt/scopes.ts:6-10,
   public-state.ts:77). The Hunt status line reads that copy, so it lags up to 15 s while the same
   leader Hunt in core is 1 s old (2.2 item 1). The fork adds Achievement Hunt progress text to config
   the same way. The public field lists (`configFields`, `configExtraKeys`, `publicStateFields`,
   `actionDomains`) are hand-kept; only per-character fields have a registry with a test
   (character-fields.ts, DSH-007).
3. **The dashboard recomputes rules other owners already own** (2.3): the farming profile owner,
   the follower routing ban, the stand-full check (written four ways), Cave entry, reserved bag
   slots, priority defaults and ranges, the merchant Cipher rule, and game formulas. Each copy can
   drift from its owner, and some already have (the merchant follower case, the stand-full count).
4. **Writes around the action client.** Seven coordinator writes in seven files use plain `fetch`
   and skip the shared cancel, refresh and session-loss handling (2.4).
5. **The status report is a decision input, and reporting changes state.** The status POST is the
   coordinator tick (DSH-001), and `snapshot` captures deaths, sets the event rejoin flag and flushes
   combat lines while it builds the report (shared.js:2837-2852, DSH-033). The fork adds `soloKills`
   to the report for scatter decisions (HEAD shared.js:3065).
